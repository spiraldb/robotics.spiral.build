# Workflow activity: agentic data-enrichment workbench (PoC)

## Context

The Studio's Data activity answers questions the data already has columns for. Semantic questions — "show me all the moments where X happened" — need features that live only in camera pixels. The implemented **Workflow activity** (peer of Live/Data/Training/Rollout) is an operational relation workbench where a workflow (1) reads one or more tables already materialized in Spiral, (2) uses read-only Spiral SQL to define the exact candidate frames, (3) optionally asks the pinned SigLIP runner to backfill missing typed features into a Studio-owned source cache, (4) joins candidates, cached features, and other evidence with Spiral SQL, and (5) shows the resulting moments. Milestones 1–3 provide the manual end-to-end slice with authoritative live node state. Milestone 4 adds a backend-owned, OpenAI-compatible Assistant that uses bounded tools to inspect relations and propose, save, run, wait for, query, and iterate the same graph. Milestone 5 makes SQL—not a special sampling tool—the cohort boundary and makes feature definitions/cache reuse source-scoped across workflows. The saved canvas, run snapshot, and Results remain authoritative, and the canvas continues to own manual Run/Cancel.

User decision: Workflow is relation-first. Hugging Face datasets, MCAP files, and other external sources are imported outside Workflow; those import producers create Spiral relations that become Workflow Table roots. One imported MCAP may therefore appear as multiple tables on the canvas. External URLs, repositories, files, import controls, and generic mutation tools must never become Workflow nodes or Assistant tools. Periodic frame selection is ordinary read-only SQL authored against an inspected Spiral media relation with `spql.video.frames` / `frame_slice`; it is not Model configuration and does not materialize a sampled-image relation. The only executable model capability in this build is `siglip-base`, backed by `google/siglip-base-patch16-224` artifacts pinned at exact revision `7fd15f0689c79d79e38b1c2e2e2370a7bf2761ed`. Hugging Face is used here only to resolve those pinned model artifacts; dataset ingestion remains outside Workflow.

**Backend**: axum 0.8; one bounded ADBC pool (4 connections); [StorageManager](crates/spiral-robotics-storage/src/manager.rs) supplies CreateAppend ingest, atomic whole-relation replace, structural update SQL, and bounded queries. **An empty batch list is a no-op**, so the Model runner deliberately replaces with one zero-row batch carrying the planned schema. `/api/spiral/query` is read-only-gated (SELECT/WITH + mutation blocklist in [query.rs](crates/spiral-robotics-core/src/query.rs)); Workflow mutations are backend-constructed. The implemented runner uses candle 0.11, tokenizers 0.22, a dedicated blocking model task, an Arrow/image prefetch thread, persisted snapshots, shared named SSE updates, and atomic cancellation flags.

**SpiralDB import producers** (sibling checkout; these capabilities populate Spiral before a workflow reads the resulting relations; they are not Workflow node kinds):
- **HF**: `spql.parquet.read('hf://datasets/{repo}@{commit}/data/**/*.parquet')` provides globbing and range reads. Studio resolves a public repository revision and bounded recursive file tree through the Hugging Face API, then gives Spiral only commit-pinned URIs. MP4 files enter a staged relation as external `spql.io.Blob` values; `spql.mp4.dataset` produces `{ds}.assets` with `index_tier='dependency'` for sparse H.264 random access.
- **Frames**: correlated comma generator `FROM {ds}.assets a, spql.video.frames(a.media, spql.video.frame_indices(ARRAY[…])) f` with engine-side `spql.video.decode` + `spql.image.resize/to_tensor` → Arrow over ADBC (the proven training path; scoped per episode/stream/segment).
- **MCAP**: `CREATE DATASET … USING spiral.mcap FROM staged(key, blob)` produces structural relations, quarantine, and topic-specific **raw payload** relations. **No message decoding exists** (no CDR/ROS/protobuf), so MCAP camera frames still require a future decoding layer.
- **Everything is synchronous** — statements return one integer; no progress, no background jobs. The Studio owns orchestration and progress.
- `spql.ai.embed` = CLIP B/32 image-only behind a **closed allow-list by design** (plan 057 non-goal: arbitrary HF execution) — confirms the Studio backend is the right home for open-ended models. **No text embedding exists** engine-side.
- Vector (fast-follow material): `CREATE VECTOR INDEX … (metric='cosine')` + `spql.search.vector('idx', ARRAY[literal], top_k=>N)`; brute-force `spql.tensor.cosine_similarity` needs no index.
- Docs: use the generated `reference/` pages (implemented behavior); `resources/vector-index.mdx` and the `CREATE DATASET … AS SELECT` example in video.mdx are stale/wrong.

**LLM integration (implemented in Stage 4).** The trusted backend owns an OpenAI-compatible streaming Chat Completions transport and typed tool loop. Studio first honors explicit process overrides and otherwise loads the ignored, owner-readable repository-root `.env.local` itself; direnv and manual export are not required. A stored `LLM_API_KEY` is sufficient for the prototype: the backend defaults to `openai/gpt-5.6-terra` through `https://openrouter.ai/api/v1`, while `LLM_MODEL` and `LLM_BASE_URL` remain optional developer overrides. Custom providers must use HTTPS, except localhost may use HTTP. The key is used only as the backend Authorization credential: it is absent from browser contracts, Spiral documents, prompts/tool output, and public errors. Public readiness intentionally leaves provider/model fields empty and exposes only Ready or bounded temporarily-unavailable product language. Production continues to inject the same secret through its secret manager.

The provider client has a 10-second connect timeout, a 90-second request timeout, and a 2 MiB streamed-response ceiling. It retries HTTP 429, 502, and 503 at most twice after the first attempt with bounded 250/500 ms delays. Streaming text and fragmented parallel tool-call arguments are assembled from SSE; malformed/non-UTF-8 or oversized streams fail explicitly. Turn cancellation interrupts provider requests and waits, cancels a Workflow run started by that turn when it is still active, and records terminal Cancelled state without inventing a response.

**Design routing (impeccable)**: precise extension of the incumbent one-light world (like Rollout — no concept roll). New component family (node cards/edges/canvas) inside existing tokens; run states obey Exceptional-Status + Spent-Colour rules; DESIGN.md + spec/ updated after implementation (AGENTS.md).

## Architecture (design-review verdicts folded in)

### Nodes (4 kinds; edges = lineage)

1. **Table** — a qualified Spiral relation name plus the fields needed by the next node. Multiple Table roots are valid: for example, `pick_place.camera_frames` and `pick_place.joint_state` can originate from one imported MCAP. Import provenance remains in Data and is not encoded as an external-source node. Frame-addressing conventions are normalized when relations are materialized so Model executors do not fork by import origin.
2. **Model / Enrich** — executable only as capability id `siglip-base`, and only after an upstream Query has defined a candidate cohort. Each of 1–32 typed feature definitions has a safe descriptive name ending `_feature`, a human description, bounded model concept text, and structured applicability: authoritative source relation, candidate image field, and optional stream IDs. The candidate Query must project `(episode_id, stream_id, segment_index, frame_index, episode_time_ns)` plus every referenced `spql.image.Image` field. Opaque legacy concepts/output shapes and every other model id are rejected. **The feature-cache relation is server-derived from the authoritative source relation**—never from the workflow id and never caller-chosen.
3. **Query** — SQL with **`{{node:<id>}}` placeholders** for upstream relations; backend substitutes server-derived names (no SQL parsing, no identifier injection surface). Read-only-gated. Residual, accepted for a single-user studio: agent SQL can read any relation in the catalog.
4. **Result** — sink; renders rows/moments via the existing query media-preview rendering (thumbnails day one; a query can select a decoded `spql.video.frame_at` thumbnail per moment).

Validation: one or more Table roots, Models and Queries read only upstream outputs, Query references only upstream node placeholders, each Model has one upstream candidate Query and exactly one authoritative source Table in its ancestry, and Result is terminal. Allowed lineage transitions are Table→Query, Query→Model, Query→Query, Model→Query, and Query→Result. A final Query can therefore consume both the candidate cohort and the shared feature cache, while other Table roots such as joint state join only after enrichment.

### Feature storage & re-runs

- **One wide cache per authoritative source relation.** Its exact non-null key is `(episode_id, stream_id, segment_index, frame_index, episode_time_ns)`. Every derived feature is a nullable `Float32`; decoded images are never stored. A workflow asks only for its candidate keys and typed features. Existing unrelated cache rows and compatible feature columns survive, and the runner computes only missing applicable cells. Rows outside a feature's optional stream applicability remain null without being treated as missing work.
- **Studio-owned feature registry.** `workflow.feature_registry` records source/cache relation, feature name, description, concept, media field, stream applicability, pinned producer/model/revision, `sigmoid_probability_0_1` value semantics, definition version, and timestamps. Exact same-name definitions for the same source are reused; incompatible same-name definitions fail explicitly. Cache keys cannot collide across sources because every source receives a distinct deterministic cache relation.
- **Atomic full publication.** The runner reads the existing cache and registry, assembles their complete successor Arrow batches, then Replaces both relations inside one ADBC transaction. Empty cohorts still publish the planned schemas. Cancellation/failure before commit leaves the prior committed cache and registry unchanged; canonical Dataset/video relations are never mutated or replaced.
- **Deterministic reuse.** Candidate identity is length-delimited and includes all five stable keys. Registry provenance binds a feature to its source, applicability, concept, pinned model repository, and artifact revision. A second workflow over the same source reuses already-populated cells and scores only missing candidate/feature pairs; another source derives another cache and cannot collide.
- A saved graph change keeps prior query rows visibly stale until replacement. **One active run per workflow** is admitted; concurrent runs are rejected.

### Execution (WorkflowManager, TrainingManager pattern)

- Validate → topological order → **sequential node execution**. Nonterminal Queries become scoped read-only subqueries. A Model executes its upstream candidate SQL, then a blocking candle task and capacity-2 image-prefetch channel fill only the missing applicable feature cells. The final Query joins candidate, cache, and other upstream evidence.
- Chunk rows derive from the decoded float input budget: `budget ÷ (image_size × image_size × 3 × sizeof(f32))`, clamped to 1–16 rows. The default budget is 8 MiB and `SPIRAL_WORKFLOW_MODEL_INPUT_MIB` may override it. The candidate Query owns video selection and decode; its resulting raw `spql.image.Image` values pass through the same pinned backend processor as already-decoded image relations.
- `WorkflowRunSnapshot` publishes truthful `Pending`, `Validating`, `Loading`, `Running{completed,total}`, `Complete`, `CompleteWithWarnings`, `Failed`, `Stale`, `Cancelling`, and `Cancelled` node states through the existing `workflow_snapshot` / `workflow_update` event path. Phase changes, materialization invalidation, and terminal model metadata persist; chunk progress is broadcast without inventing an ETA.
- **Failures:** malformed candidate images are quarantined and processing continues. The snapshot records the count and first 20 examples. Any model-load, cache/registry compatibility, or atomic publication failure fails the node. Quarantining **more than 50% of candidate rows needing feature backfill** fails the run; a nonzero bounded quarantine at or below half finishes as `CompleteWithWarnings`. The previous committed cache/registry remains authoritative unless the successor transaction commits.
- **Lease boundary**: import DDL belongs to Data's ingestion path, not `WorkflowManager`. Workflow execution starts only after its source relations exist. Destination/import admission remains linearized against active Workflow work, and Model publication mutates only the server-derived Studio feature cache plus registry.
- **ModelRunner:** `hf-hub` resolves only `config.json`, `preprocessor_config.json`, `tokenizer.json`, and `model.safetensors` from the exact pinned model revision. It tries Metal first on macOS; if Metal creation or SigLIP initialization fails, it truthfully records a CPU fallback warning and the actual device. Other platforms use CPU and report that fact. Artifact/network failures fail Loading with an actionable message; no network-availability guarantee is implied.
- **Scoring contract:** the text tower runs once per Model run over prompts of the form `This is a photo of {concept}.`; the runner validates the pinned processor's 224×224 size, PIL bicubic resample mode, rescale factor, and channel mean/std, then applies that processor to candidate images. L2-normalized image/text features pass through the model's learned logit scale and bias, then sigmoid. Values map to the exact registered `_feature` columns.
- **Cancellation boundaries:** cancellation is checked while reading candidates, after cache and registry reads, before and between image chunks, between received chunks, after the model task, before atomic publication, and between workflow nodes. Cancellation and atomic cache/registry publication share one gate: cancellation that wins prevents the transaction, while a transaction that commits first remains a completed Model before cancellation stops downstream nodes. The current synchronous Spiral query or candle forward may finish; its late result is discarded. Backend shutdown cancels and joins the active task. Destination/credential changes are blocked while a Workflow run is active.

### Assistant boundary (Milestone 4, implemented)

- The Assistant exposes exactly seven typed tools: `list_relations`; `describe_relations` for at most 20 qualified relations; `list_model_capabilities`; `set_workflow` for a complete validated Table/optional Model/Query/exactly-one-Result graph; `run_workflow`; `wait_for_run` for 1–60 seconds; and read-only `run_query` for 1–50 rows. There is no frame-sampling, import, arbitrary SQL mutation, provider-management, or credential tool. Query prompt serialization replaces media/tensor cells with type markers, caps ordinary string cells at 512 characters, bounds the query payload to 24 KiB, and bounds every tool result sent back to the provider to 32 KiB.
- The trusted system prompt describes only the implemented relation/model contract. For periodic inference it tells the provider to inspect the durable manifest/media schema, join the actual managed media relation, and author an ordinary read-only candidate Query using the table-function form `CROSS JOIN LATERAL spql.video.frames(..., spql.video.frame_slice(CAST(0 AS BIGINT), CAST(manifest.frames AS BIGINT), CAST(<positive stride> AS BIGINT)))` followed by `spql.video.decode`; the Query must preserve all five stable frame keys and name each image field used by a typed feature definition. Spiral's `request_index` is the selected output ordinal, so source identity is reconstructed as `frame_index = CAST(request_index AS UINT64) * CAST(stride AS UINT64)` and episode time uses that source frame. Signed `BIGINT` casts are limited to `frame_slice` arguments. The current engine does not provide `LEAD`/`LAG` for this path and does not accept a derived SELECT as a lateral source, so the provider uses an ordinary self-join on `frame_index + stride` and a bounded timestamp join with scalar aggregation for nearby joint evidence. At most one `spql.video.frames` generator may appear in each SELECT scope because multiple generators collide on generated fields such as `request_index`; paired-camera evidence therefore carries the already-decoded candidate image and uses one generator for the second camera, or isolates generators in separate CTEs. The prompt also forbids unquoted SQL-keyword aliases such as `top` in favor of descriptive aliases such as `top_cam`, and requires scalar evidence such as joint state to be represented by its own connected Table root and joined only in the final Query. The graph then connects that candidate Query to Model and to a final Query, Model to the same final Query, and any joint-state Table directly to the final Query. For full-resolution evidence the provider must discover and use an actual managed `media_relation`, and it may use only read-only Spiral functions and fields verified through relation tools; it may not invent a media relation or encode an engine workaround.
- One Assistant turn may be active for the project, and it cannot start during an active Workflow run. One user turn shares a maximum of 16 provider iterations and 48 tool calls across its initial response and every automatic continuation; rejection happens before an over-budget tool batch is persisted. User input is limited to 8,000 characters. Manual graph Apply/Run waits for the active Assistant turn, while the Assistant can change or start Workflow only through the same revision validation and run manager used by the canvas.
- `wait_for_run` may yield after at most 60 seconds while the backend continues to observe the run. The session moves to `WaitingForRun`; when the authoritative run becomes terminal, the backend appends a synthetic completion summary and automatically resumes the same turn with its remaining shared budget. There is no fabricated progress or browser timer driving the continuation.
- Public messages, safely rendered structured assistant text, and compact running/complete/failed tool summaries persist with provider-facing history as one server-owned schema-v2 envelope in the active Spiral project's `workflow_runs` relation. Assistant text supports paragraphs, `-`/`*` lists, bold markers, inline code, and fenced code blocks through typed Dioxus nodes only—never raw HTML. Tool traces stay collapsed during ordinary work like polished agent products; a completed turn labels nonfatal provider/tool retries as **recovered**, while only a terminal failed Assistant message opens the trace as needing action. Completed tools derive bounded receipts only from allow-listed safe facts: discovery/schema/model counts, saved graph name/revision, started run identity/phase, terminal run/result count, or bounded query row count. Graph/run/result receipts expose **View graph**, **View run**, or **View results** only while they match current authoritative truth; historic receipts remain inert. The `set_workflow` tool does not expose the server-owned workflow identity or revision to the provider; the backend injects both before decoding and validation.
- Each project keeps 1–20 durable Assistant conversations without silently deleting an older conversation. A conversation has a server-generated identity, creation/update timestamps, a deterministic title derived from its first user message (default **New conversation**), at most 80 public messages, and its own bounded provider history. Only the selected conversation enters provider context. Creating a conversation selects it; asking for New while the selected conversation is already pristine and empty is idempotent and performs no persistence, publication, or revision bump. Selecting another conversation does not change the Workflow graph, run, or Results. New/select are disabled while a turn or Agent-owned Workflow run is active—the user must Stop first—and at the 20-conversation bound with an explicit keep-existing-history recovery. Public capacity rejects another turn instead of trimming history; provider-only retention remains boundary-safe so it never starts with an orphaned tool result or splits a multi-result exchange.
- `GET /api/workflow/agent`, `POST /api/workflow/agent/conversations`, `PUT /api/workflow/agent/conversations/active`, `POST /api/workflow/agent/turn`, and `POST /api/workflow/agent/cancel` expose secret-free collection, selected-conversation, and turn lifecycle. Create/select use expected collection revision and server scope; turn/cancel also carry the selected conversation identity. Initial state and every collection revision publish on the shared event stream as the named `workflow_agent` event. The server treats broadcasts as wakeups and emits its latest snapshot, so a queued update from an old project scope cannot overwrite a reload. Project import/destination replacement validates the complete bounded conversation document before mutation and loads that project's document under a fresh server scope instead of merging histories. This prototype preserves valid current schema-v2 history only. Missing-schema, incompatible, future, or unreadable active-project history is reset under an atomic exact-snapshot compare-and-replace to one fresh **New conversation**; a failed reset leaves history unavailable and conversation mutation blocked. An active persisted turn found at restart becomes `Interrupted`; it is not automatically replayed, and any trailing tool-call batch missing one or more tool results is removed before Retry so provider history remains valid.
- Assistant conversation persistence and turn admission, graph save/start, recording, calibration-history mutation, import, and project replacement coordinate through the shared catalog-mutation lease. Create/select therefore cannot save old-project history between a project replacement and its Assistant reload. Recording and calibration-history admission reject an already-active Workflow/Assistant; once admitted, they block a later Workflow/Assistant admission. Import and destination changes remain blocked while a turn is active. Ordinary admission/save/start leases are not held across a provider wait.

### Engine and UI (implemented through Milestone 5)

Four panels live in the activity-owned PanelWorkspace (`workflow-relation-canvas-v3`): **Assistant** + **Node** tabbed left at 30%; **Workflow** canvas dominant upper-right; **Results** lower-right, with the initial canvas/results split at 66/34 so an empty result does not compete with the primary work. The Assistant is a compact one-light thread with a fixed header, product-level readiness, an accessible conversation selector whose populated labels include message counts, a concise typed **New** action, durable user/assistant/synthetic messages, safe structured text, streaming and waiting state, collapsible completed tool traces, contextual receipts, near-bottom auto-follow plus **Jump to latest**, and an autosizing 8,000-character composer. Enter sends, Shift+Enter inserts a new line, and visible helper text explains the current shortcut or disabled reason; Send/Stop/Retry remain typed actions. Unsent composer text is shell-hoisted per project scope and conversation, survives activity/Settings view unmounts, and clears only after the matching scoped turn is accepted. Conversation controls require an authoritative Spiral catalog/history store and become disabled with specific recovery when it is unavailable. Only live turn status announces; streaming token deltas and restored history do not replay through a live region. Provider implementation, model slug, credential names, and configuration instructions never appear in the product surface; temporary provider failure keeps the same stable Assistant and a bounded retry message without showing a fake active turn. The runnable default is Table→Query→Result; controlled **Add model** preserves that Query as the candidate-cohort node, inserts Model plus a generated final feature-join Query, and produces the visible Table→candidate Query→Model→final Query→Result lineage. **Remove model** removes the generated join and makes the candidate Query terminal again. The Model inspector edits typed feature name, description, concept, candidate image field, optional streams, and shows the deterministic source/cache truth; untouched definitions produce one consolidated completion message, not four empty-field errors. The canvas does not expose arbitrary edge editing. Node cards are 10.5rem with 32px sibling/56px rank gaps and a matching 56px fallback rank gap so smooth-step endpoint stubs cannot overlap. Canvas and panel resize bursts refit once after measured layout, while manual Fit enforces the same 0.70 floor. This keeps the expected five-rank, six-node, two-Table lineage readable and fully visible at the 1024 CSS-pixel desktop minimum. Selected cards expose `aria-current`. The canvas owns manual Run/Cancel, while an active Assistant turn may use its backend `run_workflow` tool. Selecting or keyboard-activating a node opens its inspector without auto-switching away from Assistant on initial render.

- `GET /api/workflow/capabilities` advertises schema version 3, executable `siglip-base`, the exact pinned repository/revision, SQL-candidate and typed-feature contract, feature limit, and Metal-first/CPU-fallback policy. No other model variant is advertised. `GET /api/workflow/relations` enumerates durable relations from the active Spiral ADBC catalog and describes Arrow fields, nullability, and semantic types. Named `workflow_agent` events on `/api/events` carry the initial snapshot and subsequent collection revisions; browser reconciliation accepts only monotonic updates within a server scope and rejects late bootstrap or command responses that would regress newer streamed state.
- The backend owns identity, revisions, qualified relation substitution, read-only admission, 1,000-row/4MiB query bounds, sequential topological execution, source-derived cache identity, typed feature provenance, and one active run per workflow. Exactly one terminal Result is required and every other node must contribute to it. Phase transitions and terminal states persist; a restart converts an in-flight run to Interrupted. A rerun keeps prior rows visibly Stale until replacement. Cancellation becomes Cancelling immediately, checks between phases, and discards a late ADBC completion before publishing Cancelled.
- The Table inspector selects an authoritative discovered relation. The Model inspector shows the single capability and edits structured feature definitions: safe `_feature` name, description, model concept, candidate image field, optional stream IDs, normalized source, and server-derived shared cache. It also renders actual device, bounded feature-cell progress, quarantine, warnings, decode/inference timing, fingerprint, and computed/reused state. The Query inspector edits exact `{{node:<id>}}` SQL. Apply is explicit and revision checked; a newer saved revision never overwrites a dirty local draft, and the only discard path is the explicit **Reload saved** action. Run and Apply remain disabled with an on-page reason while state is unknown or validation fails.
- The canvas separates neutral edit identity (**Saved · rN** or **Modified**) from semantic run state. Validating/Running/Cancelling is blue, Complete green, Complete-with-warnings ochre, Failed red, and Cancelled/Interrupted neutral. Results empty and stale states explain the actual run phase; valid cancelled/interrupted/failed recovery offers **Run again** without replacing the canvas's normal manual-run authority.
- Results reuse Data's media-aware query renderer for real schema, rows, images, video references, truncation, elapsed time, empty responses, failures, and stale prior results. Exact `spql.image.Image` values render as bounded previews directly in their schema cells with contextual episode/stream/frame alt text; their score, identity/time/frame, joint, and other fields remain ordinary neighboring cells. Live state reconciliation preserves canvas geometry and does not steal panel focus.

Node cards keep the bench vocabulary: paper, hairline, 4px radius, compact sentence-case type, and semantic Pending/Validating/Loading/Running/Complete/Complete-with-warnings/Failed/Stale/Cancelling/Cancelled states. Model cards show bounded completed/total feature cells; SQL phases use stable indeterminate language rather than fabricated percentages or ETA. The canvas uses a subtle dot grid on `--tone-viewport`, maps `--df-*` to tone tokens, and omits the MiniMap.

### Session workarounds recorded after the successful demonstration

- Spiral currently declares generator-derived identity fields nullable even though the live rows are non-null. Studio therefore accepts nullable declarations for candidate keys while still rejecting every row-level null. For feature-cache/hash-join compatibility, only `frame_index` and `episode_time_ns` are emitted nullable; all five key values are runtime-required and registry/cache readers reject nulls.
- A temporary revision-16 local API edit narrowed an earlier broad score-increase predicate to the intended `< 0.5 → >= 0.5` crossing while the trusted prompt was being corrected. The delivered revision-20 demonstration was independently generated and run by Terra with the corrected predicate, so the direct edit is not required for the final flow.
- The pinned dioxus-flow/Dioxus development renderer can flood debug signal-lifetime diagnostics and eventually overflow a worker stack after repeated topology hot reloads. Demo capture used a clean release preview with `--debug-symbols false`; release-mode source changes were handled by an explicit clean restart because the live release rebuild path can race wasm-opt temporary files. This is preview tooling isolation, not Workflow execution logic.
- The in-app browser exposes screenshots rather than a direct video stream. The final session therefore captured the real UI at 8 FPS and encoded those frames to 30 FPS H.264; no state was mocked, skipped, or recreated for the recording.
- No Hugging Face dataset or MCAP ingestion is part of the Workflow verification path through Stage 5.

## Spiral native enrichment wishlist

- A transactional multi-relation streaming Replace/upsert builder so Studio can publish a cache and its registry without assembling complete successor relations in memory.
- Keyed merge/upsert for nullable feature columns, including an explicit “fill missing cells only” mode over composite frame identity.
- Authoritative catalog relation/content version fingerprints suitable for cross-run cache validation without rescanning every candidate payload.
- Rust ADBC ergonomics for typed transaction guards, bounded batch-size negotiation, and cooperative query cancellation.

## Risks (ranked by the design review)

1. SigLIP CPU fallback is truthful but materially slower than Metal in the recorded development spike; the UI exposes the actual device and measured run timings rather than promising parity.
2. Provider compatibility is intentionally limited to the implemented OpenAI-compatible streaming Chat Completions/tool-call shape; availability, model behavior, and latency remain external-service facts rather than Studio guarantees.
3. LeRobot layout variance across versions (isolated module, one known-good repo first).
4. In-engine decode and artifact/model cold-load time vary with media, cache, host, and services; measured run evidence offers no throughput or network guarantee.
5. MCAP vision gap is engine-truth (no decoding) — structure queries always work; frames are stretch via studio-side protobuf decode.
