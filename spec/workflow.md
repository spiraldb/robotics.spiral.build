# Workflow activity: agentic data-enrichment workbench (PoC)

## Context

The Studio's Data activity answers questions the data already has columns for. Semantic questions — "show me all the moments where X happened" — need features that live only in camera pixels. The implemented **Workflow activity** (peer of Live/Data/Training/Rollout) is a node-based workbench where a workflow (1) reads one or more tables already materialized in Spiral, (2) runs pinned SigLIP safetensors over decoded images or durable video manifests via **candle in the Studio backend** to materialize a derived Spiral relation, (3) queries that relation with Spiral SQL, and (4) shows resulting moments. Milestones 1–3 provide the manual end-to-end slice with authoritative live node state. The Assistant remains unavailable; the vendor-neutral LLM tool-use loop is Milestone 4, not shipped behavior.

User decision: Workflow is relation-first. Hugging Face datasets, MCAP files, and other external sources are imported outside Workflow; those import producers create Spiral relations that become Workflow Table roots. One imported MCAP may therefore appear as multiple tables on the canvas. External URLs, repositories, files, and import controls must never become Workflow nodes. The only executable model capability in this build is `siglip-base`, backed by `google/siglip-base-patch16-224` artifacts pinned at exact revision `7fd15f0689c79d79e38b1c2e2e2370a7bf2761ed`. Hugging Face is used here only to resolve those pinned model artifacts; dataset ingestion remains outside Workflow and is not implemented by Milestone 3.

## Load-bearing research facts

**Frontend** (Dioxus 0.7.10): adding an activity is a known mechanical 16-point edit list ([activity.rs](crates/spiral-robotics-studio/src/frontend/app/activity.rs), [routes.rs](crates/spiral-robotics-studio/src/frontend/app/routes.rs), [shell.rs](crates/spiral-robotics-studio/src/frontend/app/shell.rs), icons, notifications, workspace guards, tailwind.css, spec/). [TrainingWorkspace](crates/spiral-robotics-studio/src/frontend/screens/training/workspace.rs) is the template for an activity owning its own `PanelWorkspace` (no Timeline). Controllers = Copy structs of Signals hoisted in `StudioShell`. One SSE stream `/api/events` (named events, reconnect loop) carries all job progress. Query media previews (`semantic_type`, inline image cells, video previews) landed in commit `29d2c7a` and are the rendering path Results now reuse.

**dioxus-flow** (user's crate, git dep, pin a rev): dioxus 0.7.10 exact match; pointer-events (no conflict with panels' HTML5 drag-docking); signals-owned nodes/edges; custom `node_view` (Tailwind-friendly) + `Handle`s; controlled topology changes; `FlowHandle::auto_layout(LeftToRight)+fit_view`; `--df-*` CSS vars mapped to `--tone-*`; exports `STYLESHEET`.

**Backend**: axum 0.8; one bounded ADBC pool (4 connections); [StorageManager](crates/spiral-robotics-studio-backend/src/backend/storage/manager.rs) supplies CreateAppend ingest, atomic whole-relation replace, structural update SQL, and bounded queries. **An empty batch list is a no-op**, so the Model runner deliberately replaces with one zero-row batch carrying the planned schema. `/api/spiral/query` is read-only-gated (SELECT/WITH + mutation blocklist in [query.rs](crates/spiral-robotics-core/src/query.rs)); Workflow mutations are backend-constructed. The implemented runner uses candle 0.11, tokenizers 0.22, a dedicated blocking model task, an Arrow/image prefetch thread, persisted snapshots, shared named SSE updates, and atomic cancellation flags.

**SpiralDB import producers** (sibling checkout; these capabilities populate Spiral before a workflow reads the resulting relations; they are not Workflow node kinds):
- **HF**: `spql.parquet.read('hf://datasets/{repo}@{rev}/data/**/*.parquet')` works (globbing, range reads, `HF_TOKEN` env). `spql.blob.external(uri, mime_type=>'video/mp4')` = zero-copy remote references; `spql.mp4.dataset` over a staged blob table → `{ds}.assets` (media + video_index; `index_tier='dependency'` = sparse H.264 random access — exactly the frame-sampling workload). No SQL directory listing → backend constructs mp4 URI lists from LeRobot `meta/info.json` (reqwest).
- **Frames**: correlated comma generator `FROM {ds}.assets a, spql.video.frames(a.media, spql.video.frame_indices(ARRAY[…])) f` with engine-side `spql.video.decode` + `spql.image.resize/to_tensor` → Arrow over ADBC (the proven training path; scoped per episode/stream/segment).
- **MCAP**: `CREATE DATASET … USING spql.mcap.dataset FROM staged(key, blob)` → structure relations (files/topics/channels/messages/chunks + per-topic **raw payload** tables). **No message decoding exists** (no CDR/ROS/protobuf; the `convention` option is dead code) → MCAP camera frames require studio-side payload decoding (protobuf/foxglove `CompressedImage` → JPEG first; CDR later).
- **Everything is synchronous** — statements return one integer; no progress, no background jobs. The Studio owns orchestration and progress.
- `spql.ai.embed` = CLIP B/32 image-only behind a **closed allow-list by design** (plan 057 non-goal: arbitrary HF execution) — confirms the Studio backend is the right home for open-ended models. **No text embedding exists** engine-side.
- Vector (fast-follow material): `CREATE VECTOR INDEX … (metric='cosine')` + `spql.search.vector('idx', ARRAY[literal], top_k=>N)`; brute-force `spql.tensor.cosine_similarity` needs no index.
- Docs: use the generated `reference/` pages (implemented behavior); `resources/vector-index.mdx` and the `CREATE DATASET … AS SELECT` example in video.mdx are stale/wrong.

**LLM integration remains a Stage-4 requirement, not current behavior.** The accepted direction is a vendor-neutral OpenAI-compatible chat-completions + tool-calling loop with backend-scoped secrets. Milestone 3 adds no provider configuration, agent transport, agent progress, or automatic graph authoring.

**Design routing (impeccable)**: precise extension of the incumbent one-light world (like Rollout — no concept roll). New component family (node cards/edges/canvas) inside existing tokens; run states obey Exceptional-Status + Spent-Colour rules; DESIGN.md + spec/ updated after implementation (AGENTS.md).

## Architecture (design-review verdicts folded in)

### Nodes (4 kinds; edges = lineage)

1. **Table** — a qualified Spiral relation name plus the fields needed by the next node. Multiple Table roots are valid: for example, `pick_place.camera_frames` and `pick_place.joint_state` can originate from one imported MCAP. Import provenance remains in Data and is not encoded as an external-source node. Frame-addressing conventions are normalized when relations are materialized so Model executors do not fork by import origin.
2. **Model** — executable only as capability id `siglip-base`. Its typed configuration is one upstream media field and 1–32 visual concepts (maximum 80 characters each); opaque legacy configuration and any other model id are rejected. The input must be either a direct `spql.image.Image` column or the `media_relation` field of a durable video-segment manifest containing `episode_id`, `stream_id`, `segment_index`, `timeline_offset_ns`, `fps`, and `frames`. **The output relation name is server-derived** from stable workflow/node identifier components — never caller-chosen. Concepts are trimmed, case-insensitively deduplicated, converted to collision-free `score_<slug>` fields, and echoed as the authoritative concept→column map.
3. **Query** — SQL with **`{{node:<id>}}` placeholders** for upstream relations; backend substitutes server-derived names (no SQL parsing, no identifier injection surface). Read-only-gated. Residual, accepted for a single-user studio: agent SQL can read any relation in the catalog.
4. **Result** — sink; renders rows/moments via the existing query media-preview rendering (thumbnails day one; a query can select a decoded `spql.video.frame_at` thumbnail per moment).

Validation: one or more Table roots, Models and Queries read only upstream relation outputs, Query references only upstream node placeholders, and Result is terminal. Allowed lineage transitions are Table→Model, Table→Query, Model→Query, and Query→Result.

### Feature storage & re-runs

- **One wide relation per Model node.** Direct-image inputs retain every upstream field except the pixel-heavy selected image column, then append non-null `Float32` score fields. Video-manifest inputs normalize to `(episode_id, stream_id, segment_index, frame_index, episode_time_ns, score_<slug>…)`. Conjunctive moment queries therefore need one scan and no pivots/self-joins.
- **Zero-row replace before materialization.** The runner writes one zero-row batch of the planned schema through atomic replace, which clears stale rows, creates the relation on first run, and fixes its schema before chunk 1. Successful score chunks append afterward. Empty input still leaves the correct empty relation. Cancellation or a pipeline failure clears a partially materialized relation back to that empty schema.
- **Deterministic reuse.** The fingerprint covers the pinned model id/revision, qualified input relation, selected media field, ordered resolved concepts/columns, and the upstream Arrow row stream. Durable Studio video manifests additionally bind reuse to payload SHA-256 or bounded byte reads; manifests without payload identity run successfully but warn and recompute. A match is reused only when the persisted output relation still has the expected schema and row count.
- A saved graph change keeps prior query rows visibly stale until replacement. **One active run per workflow** is admitted; concurrent runs are rejected.

### Execution (WorkflowManager, TrainingManager pattern)

- Validate → topological order → **sequential node execution**. A Model runs in one blocking task while a capacity-2 synchronous channel prefetches direct-image batches or the next in-engine video decode chunks. This overlaps bounded Spiral reads/decode with candle scoring without opening unbounded work.
- Chunk rows derive from the decoded float input budget: `budget ÷ (image_size × image_size × 3 × sizeof(f32))`, clamped to 1–16 rows. The default budget is 8 MiB and `SPIRAL_WORKFLOW_MODEL_INPUT_MIB` may override it. Video frame SQL is scoped to one episode/stream/segment and uses `spql.video.frames` → `spql.video.decode`; the raw decoded image then passes through the same pinned application-side processor as direct image rows. At most 10,000 manifest segments are admitted.
- `WorkflowRunSnapshot` publishes truthful `Pending`, `Validating`, `Loading`, `Running{completed,total}`, `Complete`, `CompleteWithWarnings`, `Failed`, `Stale`, `Cancelling`, and `Cancelled` node states through the existing `workflow_snapshot` / `workflow_update` event path. Phase changes, materialization invalidation, and terminal model metadata persist; chunk progress is broadcast without inventing an ETA.
- **Failures:** malformed direct image rows, missing decoded video frames, and bounded video read/decode failures are quarantined and processing continues. The snapshot records the count and first 20 examples. Any model-load/write/schema failure fails the node, and quarantining **more than 50% of input rows** fails the run and empties the derived relation. A nonzero bounded quarantine that remains at or below half finishes as `CompleteWithWarnings`.
- **Lease boundary**: import DDL (staged-table creation and `CREATE DATASET`) belongs to Data's ingestion path, not `WorkflowManager`. Workflow execution starts only after its input relations exist. Feature-relation writes and snapshot persistence hold no import lease (CAS-retry precedent: training snapshots), so model/query phases operate over existing Spiral relations.
- **ModelRunner:** `hf-hub` resolves only `config.json`, `preprocessor_config.json`, `tokenizer.json`, and `model.safetensors` from the exact pinned model revision. It tries Metal first on macOS; if Metal creation or SigLIP initialization fails, it truthfully records a CPU fallback warning and the actual device. Other platforms use CPU and report that fact. Artifact/network failures fail Loading with an actionable message; no network-availability guarantee is implied.
- **Scoring contract:** the text tower runs once per Model run over prompts of the form `This is a photo of {concept}.`; the runner validates the pinned processor's 224×224 size, PIL bicubic resample mode, rescale factor, and channel mean/std, then applies that one processor to both direct images and raw engine-decoded video frames. L2-normalized image/text features pass through the model's learned logit scale and bias, then sigmoid. The resulting calibrated values map positionally to the server-derived score columns.
- **Cancellation boundaries:** cancellation is checked while scanning/fingerprinting rows, before and between prefetch/decode chunks, between received chunks, after the model task, and between workflow nodes. The current synchronous Spiral decode or candle forward is allowed to finish; its late result is discarded, partial model output is cleared, and terminal publication is linearized against Cancel. Backend shutdown cancels and joins the active task. Destination/credential changes are blocked while a Workflow run is active.

### Assistant boundary (Milestone 4, unavailable)

- Milestone 3 has no LLM/provider configuration, agent endpoint, chat turn, tool loop, agent-authored graph, automatic continuation, or synthetic progress. The Assistant panel says it is not connected and owns no run action.
- Milestone 4 retains the accepted vendor-neutral, backend-owned, read-only/tool-mediated direction. Its exact provider UX, tool set, and long-run turn lifecycle remain future work and are not part of the Milestone-3 contract.

### Engine and UI (implemented through Milestone 3)

Four panels live in the activity-owned PanelWorkspace (`workflow-relation-canvas-v2`): **Assistant** + **Node** tabbed left at 30%; **Workflow** canvas dominant upper-right; **Results** lower-right. The runnable default is Table→Query→Result; a controlled **Add model** action inserts one SigLIP node between the first Table→Query edge, updates that Query placeholder, selects the new node, and triggers left-to-right layout. **Remove model** reconnects the Table directly to Query and rewrites the placeholder. The canvas does not expose arbitrary edge editing. Reopening a canvas whose topology changed also lays it out after the panel becomes measurable; unchanged topology is fitted without discarding saved geometry. Assistant remains explicitly unavailable and has no run authority. Selecting or keyboard-activating a node opens its inspector without auto-switching away from Assistant on initial render.

- `GET /api/workflow/capabilities` advertises schema version 2, executable `siglip-base`, the exact pinned repository/revision, input contract, concept limit, and Metal-first/CPU-fallback policy. No other model variant is advertised. `GET /api/workflow/relations` enumerates durable relations from the active Spiral ADBC catalog and describes Arrow fields, nullability, and semantic types. Catalog row counts are omitted; relations whose extension schema this Studio build cannot decode are skipped and the response marks itself incomplete with a limitation.
- `GET/PUT /api/workflow`, `GET /api/workflow/snapshot`, and `POST /api/workflow/run|cancel` own the saved graph and run lifecycle. The full saved state also reconnects through named `workflow_snapshot` / `workflow_update` events on the existing `/api/events` stream.
- The backend owns identity, revisions, qualified relation substitution, read-only admission, 1,000-row/4MiB query bounds, sequential topological execution, derived Model relation/score names, and one active run per workflow. Exactly one terminal Result is required and every other node must contribute to it. A Model must have exactly one Table input and a Query output.
- The graph and latest run snapshot persist atomically as one server-owned document in Spiral's `workflow_runs` relation. Phase transitions and terminal states persist; a restart converts an in-flight run to Interrupted. A rerun keeps prior rows visibly Stale until replacement. Cancellation becomes Cancelling immediately, checks between phases, and discards a late ADBC completion before publishing Cancelled.
- The Table inspector selects an authoritative discovered relation. The Model inspector shows the single capability, filters the upstream fields to direct `spql.image.Image` values or a valid video-manifest `media_relation`, accepts one visual concept per line, previews the server-derived score-column mapping, and renders actual device, bounded progress, quarantine, warnings, decode/inference timing, fingerprint, and computed/reused state. The Query inspector edits exact `{{node:<id>}}` SQL. Apply is explicit and revision checked; a newer saved revision never overwrites a dirty local draft, and the only discard path is the explicit **Reload saved** action. Run and Apply remain disabled with an on-page reason while state is unknown or validation fails.
- Results reuse Data's media-aware query renderer for real schema, rows, images, video references, truncation, elapsed time, empty responses, failures, and stale prior results. Live state reconciliation preserves canvas geometry and does not steal panel focus.

Node cards keep the bench vocabulary: paper, hairline, 4px radius, compact sentence-case type, and semantic Pending/Validating/Loading/Running/Complete/Complete-with-warnings/Failed/Stale/Cancelling/Cancelled states. Running cards show bounded row counts, never fabricated percentages or ETA. The canvas uses a subtle dot grid on `--tone-viewport`, maps `--df-*` to tone tokens, and omits the MiniMap.

## Milestones

0. **Day-1 spike (implemented)** — candle-transformers SigLIP image+text towers and tokenizer exercised on Metal and CPU against the exact pinned artifacts. The warmed full calibrated image+text forward observed in the spike was 0.918 s on Metal and 10.120 s on CPU on the development machine. These are implementation evidence, not performance guarantees; the production runner separately caches text features for a run and measures image-chunk inference.
1. **Canvas scaffold (implemented)** — fifth activity registered beside Data and before Training; dioxus-flow pinned/themed; relation-first five-node example; selection + read-only Node inspector; `WorkflowController` hoisted; four-panel desktop workspace verified. No backend execution, assistant turns, or result rows are implied.
2. **Engine, SQL-only (implemented)** — frozen relation-first WorkflowSpec/API contract and capabilities; authoritative relation discovery; WorkflowManager + named SSE + Spiral persistence/reload + cancel; revision-safe Apply; Table→Query(`{{node:…}}`)→Result end-to-end over existing Spiral relations; shared media-aware Results; live-state editor. At the Milestone-2 boundary, Model execution and Assistant transport were unavailable; Milestone 3 adds Model execution while Assistant remains future work.
3. **Model node (implemented)** — exact-revision SigLIP artifact and processor resolution; direct `spql.image.Image` and durable video-manifest inputs; in-engine video frame selection/decode followed by one shared pinned bicubic processor; Metal-first execution with honest CPU fallback; budget-derived chunks and capacity-2 prefetch; calibrated concept scores; zero-row replace and chunked derived-relation persistence; deterministic fingerprint/reuse; bounded quarantine and cancellation; durable run metadata; Model inspector, controlled insertion/removal, and topology-aware auto-layout. Desktop browser QA passed.
4. **Agent chat (future)** — vendor-neutral backend LLM/tool loop and Assistant turns. No transport or execution behavior from this milestone is available yet.
5. **External ingestion in Data** — HF LeRobot import end-to-end plus MCAP import (**structure = deliverable**; protobuf CompressedImage frames = **stretch**). Each producer materializes one or more named Spiral relations; Workflow discovers those relations as Table roots but never exposes an HF/MCAP Source node or import control. LeRobot layout variance (v2/v2.1/v3) stays isolated in the ingestion module. Model variants beyond the pinned SigLIP capability are not specified by this milestone.

Each UI milestone: craft-floor loaded before edits; detector once per MANUAL_DETECTOR_REQUIRED (it skips .rs — tailwind.css is its real target); finish-reviewer + documenter close the visual work; spec/ + DESIGN.md updated after implementation.

## Verification

- Backend: unit tests cover DAG/placeholder/identifier validation, exact-one-Result ownership, typed SigLIP configuration and score-name derivation, revision admission, read-only gating, SSE names, budget chunking, direct-image decoding, video-manifest SQL/overlap validation, and stale-result behavior. Real-Spiral integration covers SQL execution, bounded rows, concurrent-run rejection, persistence/reload, cancellation, stale prior-result retention, video decode, score persistence, deterministic reuse, zero-row replacement, and shutdown cleanup.
- Model evidence: the deterministic direct-image golden produces calibrated scores of approximately `0.48523092` for “black square” and `0.00243543` for “white square” from a black image while also exercising one quarantined malformed row. An independent Transformers 4.55.4 `SiglipModel` + `SiglipImageProcessor` run at the same exact artifact revision produced `0.48523283` and `0.00243547`. Real video end-to-end runs on the development machine observed roughly 62–72 ms of in-engine decode for two frames and 18–21 ms of SigLIP image inference on Metal. Together with the spike's warmed 0.918 s Metal / 10.120 s CPU full-forward observations, these timings are test evidence only—not benchmarks, SLAs, cold-load estimates, or guarantees for another host.
- Resource-tree teardown validates Spiral's engine-owned cascade contract: Studio first validates the exact qualified Dataset target it owns, then issues `DROP DATASET IF EXISTS <qualified_dataset> CASCADE`. Spiral removes the Dataset and its complete nested resource tree transactionally; the E2E cleanup separately removes only the Studio-created source view and test-owned root relations, and asserts that no test namespace resources remain.
- UI: interaction-language coverage is green and browser QA passed for the desktop workspace. Capture: `/private/tmp/rerobot-workflow-stage3-desktop.png`.
- Assistant/agent verification is intentionally absent because Milestone 4 is not implemented. Likewise, no HF dataset or MCAP ingestion is part of the Workflow verification path.

## Risks (ranked by the design review)

1. SigLIP CPU fallback is truthful but materially slower than Metal in the recorded development spike; the UI exposes the actual device and measured run timings rather than promising parity.
2. Agent turn lifecycle remains Milestone-4 design work; no automatic kickoff/resume behavior is promised by Stage 3.
3. LeRobot layout variance across versions (isolated module, one known-good repo first).
4. In-engine decode and artifact/model cold-load time vary with media, cache, host, and services; Stage 3 reports measured run evidence but offers no throughput or network guarantee.
5. MCAP vision gap is engine-truth (no decoding) — structure queries always work; frames are stretch via studio-side protobuf decode.
